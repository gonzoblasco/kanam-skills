# Frontend UI Engineering

## Overview

Build production-quality user interfaces that are accessible, performant, and visually polished. This skill integrates **accessibility standards (WCAG 2.1 AA)**, **design system adherence**, and **component generation prompts** to create UIs that look like they were built by a design-aware engineer — not generated by AI.

## When to Use

- Building new UI components or pages
- Modifying existing user-facing interfaces
- Implementing responsive layouts
- Adding interactivity or state management
- Fixing visual, accessibility, or UX issues
- Creating reusable component patterns from design specs

## 🎨 Phase 1: Design System Integration

### File Structure (Colocated Components)

```
src/components/
  TaskList/
    TaskList.tsx           # Component implementation
    TaskList.test.tsx      # Tests + accessibility checks
    TaskList.stories.tsx   # Storybook stories
    use-task-list.ts       # Custom hook (complex state)
    types.ts               # Component-specific types
    _story-prompt.md       # AI generation prompt for component
```

### Design Tokens Integration

When creating components, ensure alignment with:
- **Color palette**: Use semantic tokens (`text-primary`, `bg-surface`) not raw hex values
- **Typography hierarchy**: Follow the design system's type scale
- **Spacing scale**: Use consistent increments (0.25rem or equivalent)
- **Border radius**: Consistent values from design tokens
- **Motion**: Respect motion preferences and transition durations

## ♿ Phase 2: Accessibility (WCAG 2.1 AA Compliance)

Every component must meet these accessibility standards:

### ✅ Keyboard Navigation Checklist
```tsx
// Every interactive element must be keyboard accessible
<button onClick={handleClick}>✓ Accessible</button>
<div onClick={handleClick}>✗ Not focusable — FIX REQUIRED</div>
<div role="button" tabIndex={0}>✓ But prefer <button></button></div>
```

### ✅ ARIA Labels Implementation
- Label interactive elements that lack visible text: `<button aria-label="Close dialog">`
- Label form inputs with proper associations: `<label htmlFor="email">Email</label><input id="email">`
- Use `aria-label` when no visible label exists

### ✅ Focus Management Strategy
```tsx
// Move focus when content changes
function Dialog({ isOpen, onClose }) {
  const closeRef = useRef(null);
  
  useEffect(() => {
    if (isOpen) closeRef.current?.focus(); // Trap focus inside dialog
  }, [isOpen]);
  
  return <dialog open={isOpen} aria-labelledby="dialog-title">...</dialog>;
}
```

### ✅ Screen Reader Testing Workflow
1. Use screen reader (VoiceOver, NVDA, JAWS) to navigate the component
2. Check that navigation order is logical and meaningful
3. Verify that skip links work and announce content properly
4. Ensure error states are announced with clear messages
5. Test focus management on dynamic content updates

### ✅ Empty & Error States (No Blank Screens)
```tsx
// ✗ BAD — blank screen
if (tasks.length === 0) return null;

// ✓ GOOD — meaningful empty state
if (tasks.length === 0) {
  return (
    <div role="status" aria-label="No tasks">
      <EmptyStateIcon className="mx-auto h-12 w-12 text-muted"/>
      <h3>No tasks yet</h3>
      <p>Get started by creating your first task</p>
      <Button onClick={onCreateTask}>Create Task</Button>
    </div>
  );
}
```

## 📱 Phase 3: Responsive Design (Mobile-First)

### Breakpoint Strategy
Test at these critical breakpoints:
- **320px** — Minimum mobile width
- **768px** — Tablet portrait
- **1024px** — Tablet landscape
- **1440px** — Desktop entry point
- **1920px+** — Large desktop monitors

### Mobile-First Implementation
```tsx
// Tailwind: mobile-first responsive
<div className="
  grid grid-cols-1       /* Mobile: single column */
  sm:grid-cols-2         /* Small: 2 columns */
  md:grid-cols-3         /* Medium: 3 columns */
  lg:grid-cols-4         /* Large: 4 columns */
  gap-4
">
```

## ⚡ Phase 4: Loading & Transitions

### Skeleton Loading (Not Spinners)
```tsx
function TaskListSkeleton() {
  return (
    <div className="space-y-3" aria-busy="true" aria-label="Loading tasks">
      {Array.from({ length: 3 }).map((_, i) => (
        <div key={i} className="h-12 bg-muted animate-pulse rounded"/>
      ))}
    </div>
  );
}
```

### Optimistic Updates
Use optimistic UI updates with proper fallbacks when implementing mutations.

## 🔒 Phase 5: Component Architecture Patterns

### Composition over Configuration
```tsx
// ✓ GOOD — Composable
<Card>
  <CardHeader>Title</CardHeader>
  <CardBody>Content</CardBody>
</Card>

// ✗ BAD — Over-configured (prop drilling nightmare)
<Card title="Title" variant="large" bodyPadding="md">...</Card>
```

### State Management Hierarchy
```
Local state (useState)          → Component-specific UI state
Lifted state                    → Shared between 2-3 sibling components
Context                         → Theme, auth, locale (read-heavy, write-rare)
URL state (searchParams)        → Filters, pagination, shareable UI state
Server state (React Query, SWR) → Remote data with caching
Global store (Zustand, Redux)   → Complex client state app-wide
```

### Avoid Prop Drilling > 3 Levels
If you're passing props through components that don't use them, introduce context or restructure the component tree.

## 🚫 Common Anti-Patterns to Avoid

| Anti-Pattern | Why It's Bad | Production Fix |
|--------------|--------------|----------------|
| Excessive gradients | Add visual noise, clash with design systems | Flat colors matching design tokens |
| Rounded everything (rounded-2xl) | Ignores corner radius hierarchy in real designs | Consistent border-radius from design system |
| Purple/indigo everywhere | Makes every app look identical to AI-generated apps | Use project's actual color palette |
| Generic hero sections | Template-driven, no connection to actual content | Content-first layouts from real copy |
| Lorem ipsum placeholder text | Hides layout problems that real content reveals | Realistic placeholder content (approximate lengths) |
| Oversized padding everywhere | Destroys visual hierarchy and wastes space | Consistent spacing scale |
| Stock card grids | Layout shortcut that ignores information priority | Purpose-driven layouts |
| Shadow-heavy design | Layered shadows slow rendering on low-end devices | Subtle or no shadows unless design system specifies |

## 🔍 Verification Checklist

After building UI, verify all of the following:

- [ ] Component renders without console errors
- [ ] All interactive elements are keyboard accessible (Tab through the page)
- [ ] Screen reader can convey the page's content and structure
- [ ] Responsive: works at 320px, 768px, 1024px, 1440px, 1920px+
- [ ] Loading, error, and empty states all handled
- [ ] Follows the project's design system (spacing, colors, typography)
- [ ] No accessibility warnings in dev tools or axe-core
- [ ] No inline styles or arbitrary pixel values
- [ ] Focus management works correctly on dynamic content
- [ ] Color is not the sole indicator of state (use icons/text/patterns too)

## Common Rationalizations & Reality Check

| Rationalization | Reality |
|-----------------|---------|
| "Accessibility is a nice-to-have" | It's a legal requirement in many jurisdictions and an engineering quality standard. |
| "We'll make it responsive later" | Retrofitting responsive design is 3x harder than building it from the start. |
| "The design isn't final, so I'll skip styling" | Use the design system defaults. Unstyled UI creates a broken first impression for reviewers. |
| "This is just a prototype" | Prototypes become production code. Build the foundation right. |
| "The AI aesthetic is fine for now" | It signals low quality and will need rework later. Use the project's actual design system from the start. |
| "I'll add ARIA labels after the feature works" | Accessibility comes first. Implement semantic HTML and ARIA from day one. |

---

## Red Flags (Immediate Action Required)

- Components with more than 200 lines → Split them
- Inline styles or arbitrary pixel values → Extract to CSS variables or design tokens
- Missing error states, loading states, or empty states → Add all three
- No keyboard navigation testing → Test immediately
- Color as the sole indicator of state → Add icons/text/patterns
- Generic "AI look" (purple gradients, oversized cards, stock layouts) → Refactor to match design system

## AI Generation Prompts for Components

When using AI to generate components, use these prompts:

```markdown
Generate a React component that is:
1. Accessible by default (keyboard navigable, ARIA labels where needed)
2. Responsive by default (mobile-first approach)
3. Semantic HTML (use proper tags: button not div for clicks)
4. Using design tokens from the project (spacing, colors, typography)
5. No inline styles (CSS modules or styled-components)
6. Testing included (unit + E2E)

Avoid:
- Arbitrary pixel values
- Gradient backgrounds unless specified
- Color-only state indicators
- Prop drilling beyond 3 levels
```
